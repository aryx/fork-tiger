The -64 flag and what it took to make it actually run
========================================================

Written 2026-08-17, against commit 6d4002a (this repo) / the fork-c--
commit that added tests/tiger64/. Verified claims below were read in the
code or observed by running qc/tigerc; re-verify file:line references
before acting on them, they rot fast.

Context: fork-c-- (qc--, this project's backend) gained two 64-bit
targets, -alpha and -riscv64, but neither could run a real Tiger program:
tigerc only ever emitted bits32 C--, with 32-bit pointer/word widths
baked into both the generated code and this repo's own hand-written
runtime. The -64 flag (parsing/option.ml) fixes the generated-code half;
this note is about everything that flag touched and needed, plus what it
did NOT need to touch.

What -64 changes in the frontend
------------------------------------
Frame.bits_str()/ws()/align() (frontend/frame.ml) switch every Tiger
value's C-- type from bits32 to bits64 (word size 4 -> 8, alignment 4 ->
8) - stack slots, globals, `alloc_ptr`, every temp. Codegen.ml's
output_file_header splices "wordsize 64 pointersize 64" onto the emitted
"target byteorder little" pragma, since qc-- checks the source's declared
metrics against the chosen backend's and refuses a mismatch.

Two bugs surfaced compiling real Tiger programs (not caught by the
simpler hello.tig case) - both are bare-integer-literal-defaults-to-
native-word-size traps, i.e. places that emitted a plain decimal literal
expecting it to mean "32 bits" the way it always had, which silently
started meaning "64 bits" instead once wordsize flipped, mismatching a
still-32-bit-typed context:
  - frame.ml's output_footer emits the GC descriptor tables as
    "bits32[] { N, ... }" (deliberately kept 32-bit regardless of target
    - runtime/gc.c reads them as plain "unsigned" always, see below) -
    but each bare literal N now defaulted to bits64, failing elaboration
    against the bits32 array type. Fixed by appending "::bits32" to each
    literal only under -64 (leaving the 32-bit case's checked-in test
    baseline untouched).
  - codegen.ml's comparison-to-value widening was hardcoded
    "%sx32(%bit(...))" regardless of word size, feeding a bits64 temp
    under -64. Fixed to "%sx%d" tracking Frame.ws()*8.

What -64 does NOT change: this repo's own runtime
------------------------------------------------------
runtime/gc.c, stdlib/stdlib.c, stdlib/stdlib.h are hand-written C, not
generated by tigerc, and -64 has no effect on them at all - they are
shared, unconditionally, across every backend tigerc targets. They
hardcoded "unsigned" (always 32 bits, on any host) for heap pointers and
the allocation header. This is what "fork-tiger's runtime hardcoding
bits32 pointers" meant in fork-c--'s own earlier notes about why alpha's
tiger tests were blocked - not a tigerc/codegen problem, a genuinely
separate one in this repo's runtime.

Ported to uintptr_t (commit 6d4002a): heap/from_space/to_space/alloc_ptr/
space_end, the FORWARDED/SIZE_MASK bit trick, gc_forward/gc_copy/
internal_alloc, tig_sizea/tig_size (stdlib.c) and the `string` struct's
`length` field (stdlib.h) all changed from "unsigned"/"unsigned*" to
uintptr_t/uintptr_t*. uintptr_t equals plain "unsigned" on every existing
32-bit backend qc-- has (x86/ppc/sparc/mips/arm/riscv32), so this is a
no-op there - confirmed by rerunning every one of fork-c--'s own
run-tiger-*.sh scripts afterwards and matching their recorded baselines
exactly, byte for byte.

One thing deliberately NOT widened: the GC descriptor tables gc_data
points at (Cmm_GetDescriptor's return value in gc.c) stay "unsigned*"
regardless of target, matching frame.ml's own bits32-tables-stay-bits32
choice above - runtime/gc.c reads them as plain 4-byte "unsigned"
counts/flags on every target, by design, not an oversight.

This repo's .c-- runtime sources (runtime/runtime.c--, runtime/alloc.c--,
stdlib/stdlibcmm.c--) have the SAME 32-bit hardcoding as gc.c/stdlib.c
did (bits32 throughout, a "+4" header-skip offset, a 0xFFFFFFFC alignment
mask) but with no equivalent fix checked in here: unlike the C files,
there is no "uintptr_t"-style width-portable spelling in C-- - a bits32
literal genuinely has to become a bits64 one, per target. That mechanical
transform (bits32->bits64, "+4"->"+8", the alignment mask widened to
0xFFFFFFFFFFFFFFF8) lives in fork-c--'s own
tests/tiger64/regenerate-riscv64.sh, applied at generation time rather
than checked in here - the same reasoning fork-c--'s tests/tiger/
regenerate-ppc.sh already uses for its own byteorder-flip transform: qc--
depends on this repo, not the other way around, so per-backend transforms
belong on qc--'s side of that dependency, not this one's.

What was actually blocking alpha/riscv64, in order
--------------------------------------------------------
Bringing fork-c--'s tests/tiger64/ up against -riscv64 (see that repo's
own docs/claude_notes/notes_64bits.txt and notes_riscv.txt for the full
writeup) needed, in this order: (1) the two frame.ml/codegen.ml bugs
above, just to get valid bits64 C-- out of tigerc at all; (2) this
repo's own gc.c/stdlib.c/stdlib.h port, just to stop the runtime itself
from corrupting memory; (3) two bugs entirely inside qc-- (riscv64's
instruction selection was missing %quot; qc--'s own pcmap runtime had a
matching "hardcoded unsigned" bug to (2), affecting every backend, not
riscv64-specific - this was the single fix that took the suite from
"every GC-triggering test crashes" to passing on all of them). Two
narrower bugs remain open against -riscv64 (a heap corruption specific to
colmajor.tig's 2D-array pattern; a wrong exit code from merge.tig with
otherwise-correct output) - see fork-c--'s tests/tiger64/README for the
current detail, since that is where the test suite (and so the up-to-date
pass/fail count) actually lives.

===============================================================================
Follow-up: a third 64-bit backend, arm64/macOS (2026-08-25)
===============================================================================

qc-- gained a native -arm64 backend (Mach-O, this host's own architecture
on Apple Silicon - see fork-c--'s own docs/claude_notes/notes_arm64.txt).
Wiring it up here needed ZERO changes to this repo's OCaml (frontend/,
backend/codegen.ml) or C/C-- (runtime/, stdlib/) - confirms the -64
machinery this note documents is genuinely target-generic, not something
alpha/riscv64 needed patched a second time. `tigerc -64` already emits
valid bits64 C-- for -arm64 unchanged; XFORM=64 in runtime/Makefile and
stdlib/Makefile (the SAME sed block alpha/riscv64 already used) applies
unmodified.

All of the actual new work was build-plumbing, in three files:
configure (new CC_ARM64/AR_ARM64/RUN_ARM64 detection - "clang", no cross
toolchain, RUN_ARM64 always empty since this is the host's own native
architecture), runtime/Makefile and stdlib/Makefile (new BACKEND=arm64
branch, XFORM=64), plus demos/Makefile and tests/run-tests.sh needing one
genuinely new wrinkle each backend before this one didn't: no "-static"
on the final link (Apple does not support static-linking libSystem at
all) and no $(QCPCMAP)/"$QCPCMAP" on the link line (that GNU-ld linker-
script fragment has no Mach-O equivalent - ld64 has no "-T" mechanism at
all; qc--'s own -arm64 backend doesn't need one, see notes_arm64.txt for
what replaces it on qc--'s side).

Verified end to end, natively (no qemu, no cross toolchain):
  ./configure && make -C stdlib BACKEND=arm64 && make -C runtime BACKEND=arm64
  ./bin/tigerc -64 demos/hello.tig > /tmp/hello.c--
  qc -arm64 -globals -o /tmp/hello runtime/build-arm64/runtime.o \
    runtime/build-arm64/stdlib.a runtime/build-arm64/qcmm.a /tmp/hello.c--
  /tmp/hello        # "Hello, world.", exit 14 (tig_print's own return-count convention)
Also `make run-arm64` (demos/Makefile: hello, forloop, queens) and
`make test-arm64` (tests/run-tests.sh, the full tests/tiger.tests suite):
queens.tig (a genuinely non-trivial program - correctly prints all 92
solutions to 8-queens) runs correctly end to end. Full suite: 6/14
(tests/expected/tiger-arm64.txt) - exceptions/funcall/hello/merge/queens/
sieve pass; the rest fail the same way fork-c--'s own tests/tiger64/
suite does for -arm64 there (mostly "Assertion failed: (size > 0),
function internal_alloc, file gc.c, line 77" - see notes_arm64.txt in the
fork-c-- checkout for the current grouping/diagnosis of those, not
re-investigated separately here since this repo's own gc.c/stdlib.c are
unmodified and the failure mode matches qc--'s own baseline exactly).

Follow-up: plain "./configure && make" was still broken on this host
------------------------------------------------------------------------
Everything above was reachable via explicit `BACKEND=arm64`/`make
test-arm64`, but plain `./configure && make` (CLAUDE.md's own Quick Start,
and what a user actually tried) still failed: every Makefile/script here
hardcodes "x86" as its OWN default (`BACKEND ?= x86` in stdlib/Makefile
and runtime/Makefile; the top-level Makefile's `all`/`test` called those
sub-makes with no BACKEND override at all, inheriting that x86 default),
and CC32 defaults to `i686-linux-gnu-gcc` - a Linux-only cross-compiler
with no macOS equivalent, so x86 was never buildable here no matter what.
`./configure` already warned about the missing CC32, but the warning was
easy to miss among a dozen other optional-backend warnings, and `make`
itself treated it as fatal, not optional.

Fixed with a new `DEFAULT_BACKEND` (configure picks it: "x86" normally,
"arm64" only when CC32 is missing AND the host is genuinely
`uname -s`=Darwin/`uname -m`=arm64 AND clang is on PATH - checking OS, not
just CPU, matters: a Linux arm64 host, e.g. AWS Graviton, can easily have
clang without an i686 cross toolchain either, and qc--'s -arm64 backend is
Mach-O-only, so defaulting to it there would silently break Linux arm64
instead of just x86). Only the TOP-LEVEL Makefile's `all`/`test` targets
were changed to pass `BACKEND=$(DEFAULT_BACKEND)` down - stdlib/Makefile,
runtime/Makefile, demos/Makefile, tests/run-tests.sh all keep defaulting
to x86 on their own, unchanged, so every existing doc/script/workflow that
names a BACKEND explicitly (or runs one of those Makefiles directly) is
unaffected. Verified from a clean state (`rm -rf stdlib/build-arm64
runtime/build-arm64`) that plain `./configure && make` and `make test` now
succeed and reproduce the same 6/14 baseline above, with no explicit
BACKEND= anywhere on the command line.
