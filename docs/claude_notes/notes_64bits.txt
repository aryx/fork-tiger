The -64 flag and what it took to make it actually run
========================================================

Written 2026-08-17, against commit 6d4002a (this repo) / the fork-c--
commit that added tests/tiger64/. Verified claims below were read in the
code or observed by running qc/tigerc; re-verify file:line references
before acting on them, they rot fast.

Context: fork-c-- (qc--, this project's backend) gained two 64-bit
targets, -alpha and -riscv64, but neither could run a real Tiger program:
tigerc only ever emitted bits32 C--, with 32-bit pointer/word widths
baked into both the generated code and this repo's own hand-written
runtime. The -64 flag (parsing/option.ml) fixes the generated-code half;
this note is about everything that flag touched and needed, plus what it
did NOT need to touch.

What -64 changes in the frontend
------------------------------------
Frame.bits_str()/ws()/align() (frontend/frame.ml) switch every Tiger
value's C-- type from bits32 to bits64 (word size 4 -> 8, alignment 4 ->
8) - stack slots, globals, `alloc_ptr`, every temp. Codegen.ml's
output_file_header splices "wordsize 64 pointersize 64" onto the emitted
"target byteorder little" pragma, since qc-- checks the source's declared
metrics against the chosen backend's and refuses a mismatch.

Two bugs surfaced compiling real Tiger programs (not caught by the
simpler hello.tig case) - both are bare-integer-literal-defaults-to-
native-word-size traps, i.e. places that emitted a plain decimal literal
expecting it to mean "32 bits" the way it always had, which silently
started meaning "64 bits" instead once wordsize flipped, mismatching a
still-32-bit-typed context:
  - frame.ml's output_footer emits the GC descriptor tables as
    "bits32[] { N, ... }" (deliberately kept 32-bit regardless of target
    - runtime/gc.c reads them as plain "unsigned" always, see below) -
    but each bare literal N now defaulted to bits64, failing elaboration
    against the bits32 array type. Fixed by appending "::bits32" to each
    literal only under -64 (leaving the 32-bit case's checked-in test
    baseline untouched).
  - codegen.ml's comparison-to-value widening was hardcoded
    "%sx32(%bit(...))" regardless of word size, feeding a bits64 temp
    under -64. Fixed to "%sx%d" tracking Frame.ws()*8.

What -64 does NOT change: this repo's own runtime
------------------------------------------------------
runtime/gc.c, stdlib/stdlib.c, stdlib/stdlib.h are hand-written C, not
generated by tigerc, and -64 has no effect on them at all - they are
shared, unconditionally, across every backend tigerc targets. They
hardcoded "unsigned" (always 32 bits, on any host) for heap pointers and
the allocation header. This is what "fork-tiger's runtime hardcoding
bits32 pointers" meant in fork-c--'s own earlier notes about why alpha's
tiger tests were blocked - not a tigerc/codegen problem, a genuinely
separate one in this repo's runtime.

Ported to uintptr_t (commit 6d4002a): heap/from_space/to_space/alloc_ptr/
space_end, the FORWARDED/SIZE_MASK bit trick, gc_forward/gc_copy/
internal_alloc, tig_sizea/tig_size (stdlib.c) and the `string` struct's
`length` field (stdlib.h) all changed from "unsigned"/"unsigned*" to
uintptr_t/uintptr_t*. uintptr_t equals plain "unsigned" on every existing
32-bit backend qc-- has (x86/ppc/sparc/mips/arm/riscv32), so this is a
no-op there - confirmed by rerunning every one of fork-c--'s own
run-tiger-*.sh scripts afterwards and matching their recorded baselines
exactly, byte for byte.

One thing deliberately NOT widened: the GC descriptor tables gc_data
points at (Cmm_GetDescriptor's return value in gc.c) stay "unsigned*"
regardless of target, matching frame.ml's own bits32-tables-stay-bits32
choice above - runtime/gc.c reads them as plain 4-byte "unsigned"
counts/flags on every target, by design, not an oversight.

This repo's .c-- runtime sources (runtime/runtime.c--, runtime/alloc.c--,
stdlib/stdlibcmm.c--) have the SAME 32-bit hardcoding as gc.c/stdlib.c
did (bits32 throughout, a "+4" header-skip offset, a 0xFFFFFFFC alignment
mask) but with no equivalent fix checked in here: unlike the C files,
there is no "uintptr_t"-style width-portable spelling in C-- - a bits32
literal genuinely has to become a bits64 one, per target. That mechanical
transform (bits32->bits64, "+4"->"+8", the alignment mask widened to
0xFFFFFFFFFFFFFFF8) lives in fork-c--'s own
tests/tiger64/regenerate-riscv64.sh, applied at generation time rather
than checked in here - the same reasoning fork-c--'s tests/tiger/
regenerate-ppc.sh already uses for its own byteorder-flip transform: qc--
depends on this repo, not the other way around, so per-backend transforms
belong on qc--'s side of that dependency, not this one's.

What was actually blocking alpha/riscv64, in order
--------------------------------------------------------
Bringing fork-c--'s tests/tiger64/ up against -riscv64 (see that repo's
own docs/claude_notes/notes_64bits.txt and notes_riscv.txt for the full
writeup) needed, in this order: (1) the two frame.ml/codegen.ml bugs
above, just to get valid bits64 C-- out of tigerc at all; (2) this
repo's own gc.c/stdlib.c/stdlib.h port, just to stop the runtime itself
from corrupting memory; (3) two bugs entirely inside qc-- (riscv64's
instruction selection was missing %quot; qc--'s own pcmap runtime had a
matching "hardcoded unsigned" bug to (2), affecting every backend, not
riscv64-specific - this was the single fix that took the suite from
"every GC-triggering test crashes" to passing on all of them). Two
narrower bugs remain open against -riscv64 (a heap corruption specific to
colmajor.tig's 2D-array pattern; a wrong exit code from merge.tig with
otherwise-correct output) - see fork-c--'s tests/tiger64/README for the
current detail, since that is where the test suite (and so the up-to-date
pass/fail count) actually lives.

Follow-up: a third 64-bit backend, arm64/macOS (2026-08-25)
===============================================================================

qc-- gained a native -arm64 backend (Mach-O, this host's own architecture
on Apple Silicon - see fork-c--'s own docs/claude_notes/notes_arm64.txt).
Wiring it up here needed ZERO changes to this repo's OCaml (frontend/,
backend/codegen.ml) or C/C-- (runtime/, stdlib/) - confirms the -64
machinery this note documents is genuinely target-generic, not something
alpha/riscv64 needed patched a second time. `tigerc -64` already emits
valid bits64 C-- for -arm64 unchanged; XFORM=64 in runtime/Makefile and
stdlib/Makefile (the SAME sed block alpha/riscv64 already used) applies
unmodified.

All of the actual new work was build-plumbing, in three files:
configure (new CC_ARM64/AR_ARM64/RUN_ARM64 detection - "clang", no cross
toolchain, RUN_ARM64 always empty since this is the host's own native
architecture), runtime/Makefile and stdlib/Makefile (new BACKEND=arm64
branch, XFORM=64), plus demos/Makefile and tests/run-tests.sh needing one
genuinely new wrinkle each backend before this one didn't: no "-static"
on the final link (Apple does not support static-linking libSystem at
all) and no $(QCPCMAP)/"$QCPCMAP" on the link line (that GNU-ld linker-
script fragment has no Mach-O equivalent - ld64 has no "-T" mechanism at
all; qc--'s own -arm64 backend doesn't need one, see notes_arm64.txt for
what replaces it on qc--'s side).

Verified end to end, natively (no qemu, no cross toolchain):
  ./configure && make -C stdlib BACKEND=arm64 && make -C runtime BACKEND=arm64
  ./bin/tigerc -64 demos/hello.tig > /tmp/hello.c--
  qc -arm64 -globals -o /tmp/hello runtime/build-arm64/runtime.o \
    runtime/build-arm64/stdlib.a runtime/build-arm64/qcmm.a /tmp/hello.c--
  /tmp/hello        # "Hello, world.", exit 14 (tig_print's own return-count convention)
Also `make run-arm64` (demos/Makefile: hello, forloop, queens) and
`make test-arm64` (tests/run-tests.sh, the full tests/tiger.tests suite):
queens.tig (a genuinely non-trivial program - correctly prints all 92
solutions to 8-queens) runs correctly end to end. Full suite: 6/14
(tests/expected/tiger-arm64.txt) - exceptions/funcall/hello/merge/queens/
sieve pass; the rest fail the same way fork-c--'s own tests/tiger64/
suite does for -arm64 there (mostly "Assertion failed: (size > 0),
function internal_alloc, file gc.c, line 77" - see notes_arm64.txt in the
fork-c-- checkout for the current grouping/diagnosis of those, not
re-investigated separately here since this repo's own gc.c/stdlib.c are
unmodified and the failure mode matches qc--'s own baseline exactly).

Follow-up: plain "./configure && make" was still broken on this host
------------------------------------------------------------------------
Everything above was reachable via explicit `BACKEND=arm64`/`make
test-arm64`, but plain `./configure && make` (CLAUDE.md's own Quick Start,
and what a user actually tried) still failed: every Makefile/script here
hardcodes "x86" as its OWN default (`BACKEND ?= x86` in stdlib/Makefile
and runtime/Makefile; the top-level Makefile's `all`/`test` called those
sub-makes with no BACKEND override at all, inheriting that x86 default),
and CC32 defaults to `i686-linux-gnu-gcc` - a Linux-only cross-compiler
with no macOS equivalent, so x86 was never buildable here no matter what.
`./configure` already warned about the missing CC32, but the warning was
easy to miss among a dozen other optional-backend warnings, and `make`
itself treated it as fatal, not optional.

Fixed with a new `DEFAULT_BACKEND` (configure picks it: "x86" normally,
"arm64" only when CC32 is missing AND the host is genuinely
`uname -s`=Darwin/`uname -m`=arm64 AND clang is on PATH - checking OS, not
just CPU, matters: a Linux arm64 host, e.g. AWS Graviton, can easily have
clang without an i686 cross toolchain either, and qc--'s -arm64 backend is
Mach-O-only, so defaulting to it there would silently break Linux arm64
instead of just x86). Only the TOP-LEVEL Makefile's `all`/`test` targets
were changed to pass `BACKEND=$(DEFAULT_BACKEND)` down - stdlib/Makefile,
runtime/Makefile, demos/Makefile, tests/run-tests.sh all keep defaulting
to x86 on their own, unchanged, so every existing doc/script/workflow that
names a BACKEND explicitly (or runs one of those Makefiles directly) is
unaffected. Verified from a clean state (`rm -rf stdlib/build-arm64
runtime/build-arm64`) that plain `./configure && make` and `make test` now
succeed and reproduce the same 6/14 baseline above, with no explicit
BACKEND= anywhere on the command line.

Follow-up: tig_compare_str's 32-vs-64-bit ABI mismatch - 6/14 to 13/14 (2026-08-25)
===============================================================================

Chasing individual tiger-arm64 failures (qsort's "sorted by name" output
came back in the exact original, unsorted insertion order - a strong
signature of "every string comparison returns the same answer") led to a
real, general bug, not a per-test one: `frontend/main.ml`'s `imports` list
declares every runtime helper's C-- import at native word width
(`Frame.bits_str()`, "bits64" under -64) - correct for every genuine
pointer/native-Tiger-int helper, but WRONG for `tig_compare_str`
(stdlib.c), which is a real C function returning a plain 32-bit `int`.

This was never a problem in the original 32-bit-only compiler (bits32 IS
native word there, so no mismatch was possible), and stayed hidden on
every 64-bit qc-- backend that existed before -arm64 purely by ABI luck:
RISC-V64's LP64 calling convention sign-extends a 32-bit return value into
its full 64-bit register automatically, so `tig_compare_str`'s raw x0-
equivalent already held the mathematically correct 64-bit value by the
time -riscv64/-alpha's own foreign-call marshalling read it. AArch64
(confirmed empirically with a throwaway C-- probe comparing the raw result
against both possible widenings directly) does the opposite: writing a
32-bit (W) register architecturally ZERO-extends the corresponding 64-bit
(X) register, with no notion that the value was "supposed to" be signed -
so a negative strncmp() result like -1 came back as a huge positive 64-bit
number (0x00000000FFFFFFFF, not 0xFFFFFFFFFFFFFFFF) on -arm64 specifically.

Two fix shapes were tried, in order:
1. First attempt: declare tig_compare_str's import as genuinely bits32
   (special-cased in Codegen.output_file_header) and explicitly sign-
   extend its result to native width before use. This needed a real new
   Tree.exp constructor (SX32) - Tree.ml has no notion of a narrower-than-
   native integer anywhere in its type (every temp/exp is implicitly
   native-word-sized), so representing "a temp genuinely holds a 32-bit
   value" meant touching Tree.ml, tree.mli, canonical.ml (the reorder/
   linearization pass), codegen.ml, and a new Frame.ml side-table
   (bits32_temps, since frm.temps carries no width field to hang this off
   either). Built and confirmed it worked, but reverted anyway: for a
   single occurrence of this bug (compare_str is still the only case
   found), threading a width concept through the core IR was judged out
   of proportion to the problem - "add the general mechanism when a
   second real use case shows up, not preemptively."
2. What shipped instead: a plain arithmetic correction, entirely local to
   Translate.compare_str, no IR changes at all. If the raw result looks
   like a negative 32-bit value read as an unsigned/zero-extended 64-bit
   one (i.e. >= 2^31), subtract 2^32 to recover the true signed value.
   This is a no-op whenever the value is already correctly sign-extended
   (a genuine negative 64-bit number is never >= 2^31), so the exact same
   code is correct on every backend - no Option.arch64 special-casing
   needed, unlike fix #1's import-declaration override. Implemented with
   Translate's own existing eseq/CJUMP/label primitives (the same ones
   Translate.ifexp itself is built from - not called directly, since
   ifexp is defined later in the file than compare_str and reordering
   syncweb-chunked functions to fix that felt like its own can of worms).

Result: tests/run-tests.sh BACKEND=arm64 went from 6/14 to 13/14 in one
fix - every remaining string-comparison-dependent test (qsort, rb, rc4,
wf, wff) started passing, plus merge (which the earlier +4/EOF-sentinel
fix had already gotten to PASS, unaffected by this one). Only colmajor
remains, and it is not a new failure: it needs a bigger heap than the
8192-byte default to avoid a real GC-cycle-triggered crash - confirmed by
hand with TIGER_HEAPSIZE=1000000 (exit 0, byte-for-byte correct output) -
the same shape of failure fork-c--'s own tests/tiger64/README documents
for -riscv64's colmajor at the same default heap size, believed to be the
shared, not-yet-root-caused GC/register-allocator bug notes_arm.txt
diagnoses for ARM32 (a GC-required temp not always kept live across every
call site under high register pressure), not something new to -arm64.

Also regenerated (fork-c--'s own tests/tiger64/*.c-- - see that repo's
regenerate-c--.sh): colmajor.c--/merge.c--/qsort.c--/rc4.c--/rb.c--/
wf.c--/wff.c-- all changed (new temps/labels from this fix's CJUMP-based
correction); arrays.c--/exceptions.c--/forloop.c--/funcall.c--/hello.c--/
queens.c--/sieve.c-- were byte-for-byte identical (no compare_str call in
those tests), confirming the fix's blast radius is exactly the string-
comparison-using tests and nothing else.

Cross-repo footnote: fork-c--'s own copy of this test suite (tests/
tiger64/, real stdin input rather than /dev/null for merge) briefly
regressed to only 8/15 passing after this fix landed, even though every
regenerated .c-- was confirmed correct - the actual cause turned out to be
on qc--'s side (a since-abandoned arm64rec.mlb grammar rule, added then
made unnecessary by this fix's final arithmetic shape but not yet deleted,
was miscompiling unrelated runtime code by its mere presence in the
compiler used to build tigermain-arm64.o/stdlib-arm64.a - see qc--'s own
docs/claude_notes/notes_arm64.txt for the full diagnosis). Nothing to fix
here; noted in case a similar "regenerated output looks right but tests
still fail" symptom recurs - check whether the compiler, not the generated
source, is the stale/wrong half.

Follow-up: qc-- repurposes bare -arm64/-amd64 as Linux/ELF, arm64 goes
native on this dev host, amd64 joins the suite at 9/14 (2026-08-30)
===============================================================================

qc-- gained real Linux/ELF backends for arm64 and amd64 (arch/{amd64,
arm64}/*asm.ml, ELF/Linux as the default), demoting the OLD macOS/Mach-O
behaviour documented everywhere above to a separate, explicit
-arm64-mach-o/-amd64-mach-o flag pair - see qc--'s own docs/claude_notes/
notes_arm64.txt/notes_amd64.txt for that repo's side of the story. This
dev host is itself aarch64-linux (not macOS), so this is the first time
either backend has been buildable/testable here at all rather than only
on a real Apple Silicon Mac.

What changed in this repo: configure (CC_ARM64/CC_AMD64 now detected via
the ordinary detect_backend path - real cross toolchains, qemu-aarch64/
qemu-x86_64 fallback - with a new, separately-detected CC_ARM64_MACHO/
CC_AMD64_MACHO pair for the old Darwin-only behaviour, probed only on a
Darwin host), runtime/Makefile, stdlib/Makefile, demos/Makefile and
tests/run-tests.sh (new BACKEND=amd64 branch alongside arm64, both now
ordinary Linux-hosted backends - "$(CC) -static ... $(QCPCMAP)" link, no
more of the old "no -static, no QCPCMAP" special-casing, which moved to
the new arm64-mach-o/amd64-mach-o branches instead), and the top-level
Makefile (DEFAULT_BACKEND's own Darwin-without-CC32 fallback now picks
arm64-mach-o, not arm64, since plain arm64 can no longer link against
Mach-O/libSystem; new test-amd64/test-arm64-mach-o/test-amd64-mach-o
targets).

A genuine, general configure bug found and fixed along the way: multi-
alternative native_pat values (e.g. arm64's own "aarch64|arm64") were
passed through an unquoted shell variable into a case pattern - POSIX
shells do NOT treat a "|" arriving via parameter expansion as case
alternation (that splitting happens at parse time, before expansion;
verified directly against both dash and bash), so EVERY native-host
detection with more than one alternative (ppc's own "ppc|ppc64|powerpc|
powerpc64", mips's "mips|mipsel|mips64|mips64el", and now arm64's own)
silently never matched, falling through to the qemu-fallback branch even
on a genuinely native host. Never surfaced before because nobody had
actually run this configure script on real ppc/mips hardware - but it
directly broke arm64 native-detection on this very aarch64-linux dev box
(RUN_ARM64 came back pointing at qemu-aarch64 instead of empty). Fixed by
wrapping the case dispatch in `eval` so the alternation is parsed after
substitution, same idiom needed anywhere a pattern has to come from a
variable.

Cross-repo bug found and fixed in qc-- itself (not just this repo's build
files): runtime/arm64cont.s and runtime/amd64cont.s (the Cmm_unwindcont_pc
trap stub every program's runtime.o references unconditionally) were
Mach-O-only - Darwin's C symbol-mangling convention adds a leading
underscore ("_Cmm_unwindcont_pc") that ELF hosts don't use - and were
never split when the Linux/ELF backends were added, so every arm64/amd64
Linux/ELF link failed with "undefined reference to `Cmm_unwindcont_pc'"
even though qc alone compiled and linked the C-- units cleanly. Fixed by
splitting each into an ELF variant (kept the original filename, no
underscore - matches every other Linux-hosted *cont.s here) and a new
arm64machocont.s/amd64machocont.s (with the underscore, wired to the new
BACKEND=arm64-mach-o/amd64-mach-o cases) - see that repo's runtime/
Makefile and runtime/dune. Required a `dune build && make install` in the
qc-- checkout before this repo's own arm64/amd64 builds could link.

Also picked up, already fixed on qc--'s side by the time this session
started rebuilding it: a real x86-64 stack-misalignment bug (real "call"
pushes an 8-byte return address the shared frame-layout equation solver
didn't account for, so every amd64 call site was 8 bytes short of the
16-byte alignment glibc's optimized vfprintf's %xmm0-7 spill requires -
segfaulted on "call printf" under real qemu-x86_64 before the fix, silent
on macOS/libSystem's own printf under Rosetta 2) - see qc--'s own commit
for arch/amd64/amd64backend.ml's retaddr_block. Without this, amd64 would
not have gotten past hello.tig at all.

Results, natively/under qemu on this aarch64-linux host (no Mac involved):
tests/expected/tiger-arm64.txt stays 13/14 (colmajor only) - identical
bar to the old Mach-O baseline, now reached on real Linux/ELF instead.
tests/expected/tiger-amd64.txt (new) is 9/14: colmajor plus rc4/rb/wf/wff,
matching qc--'s own tests/tiger64/README findings for -amd64-mach-o
almost exactly (same four extra failures beyond colmajor/merge) - fork-
tiger's own suite input sizes happen to avoid triggering merge's wrong-
exit-code gap (present in qc--'s own harsher fixtures, not in tests/
tiger.tests' merge.tig), but hit the same underlying GC/liveness bug
colmajor/rc4/rb/wf/wff share, believed the same not-yet-root-caused issue
documented for arm64/riscv64/amd64 throughout this file and qc--'s own
notes_amd64.txt/notes_arm64.txt - not chased further here, same
"touching shared regalloc/codegen machinery, real regression risk to
every other backend" call already made for every prior occurrence.

The arm64-mach-o/amd64-mach-o (Darwin-only) tier could not be verified in
this session (no macOS host available) - the build-plumbing (configure,
Makefiles, run-tests.sh) is in place and mirrors the pre-rename arm64
code path exactly, but has not been run.
